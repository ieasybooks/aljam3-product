# Product mandate

Aljam3 serves Sharia students and Muslims who read, search, compare and cite Islamic books. Aim for a better everyday experience than Shamela.com and Turath.io, measured through real tasks rather than feature counts. A smaller, more reliable workflow is often more valuable than another option.

Consistency means web and desktop use coherent terminology, interaction patterns, navigation, and citation behavior while respecting platform conventions. Simplicity means fewer steps, clear defaults, discoverable controls, and recovery that preserves the user's work. Performance means responsive Arabic search, efficient large libraries, smooth PDF reading, and useful behavior on slow networks and modest hardware. Accuracy means faithful quotations, source metadata, edition/page references and explicit uncertainty. Quality includes accessible keyboard operation, RTL and bidirectional text, Arabic/Urdu/English localization, stable updates, offline data integrity and privacy.

Research should start with observable problems: existing issues, reproducible defects, consented support feedback, documented usability sessions, and available aggregated telemetry. The web app already records search queries/clicks; desktop includes analytics, but access and appropriate redaction must be established before using either. Do not claim analytics evidence that was not actually accessed. Existing application issues are inputs, not approved work.

Use dated competitor observations and links for the same reading/search/citation task. Distinguish observed behavior from assumptions. Do not bulk scrape or copy restricted material. State the expected user benefit, alternatives, tradeoffs, confidence and what would disprove the proposal. The owner may reject a plausible feature when evidence is weak.

Every user-visible proposal needs a screenshot of the current experience and a proposed sketch/mockup, or a clear explanation when a visual is irrelevant (for example an internal indexing fix). Mark sketches as proposed, not shipped screenshots. Show Arabic/RTL first, error/loading/empty states, keyboard focus, narrow layouts, light/dark modes as relevant, and the desktop offline state. Put assets under `proposals/<key>/` with descriptive filenames and alt text; commit them to a stable revision and link that revision in the issue so the approved experience cannot drift.

Never invent scholarly authority or present generated summaries as source text. Changes involving corpus content, OCR correction, religious conclusions, ranking neutrality, source attribution or licensing need explicit human review. Authentication, credentials, privacy, destructive migrations, update signing and deployment policy also need final human delivery approval in addition to initial scope approval. Mark such proposals `risk: human-delivery`; the gate also detects sensitive paths, but path matching cannot replace the roles' judgment.

Size measures delivery scope, not the importance of the idea. Small normally affects one workflow with limited code and no risky migration; medium spans several components or both apps; large needs staged design and careful compatibility work. Split a large idea only into independently useful, independently approved outcomes. Record estimated effort and a line budget in the implementation brief; do not treat either as a quota to consume.

Success measures should be observable: fewer failed searches, time to find/cite a passage, reading responsiveness, error rate, installation success, or a reproducible usability improvement. Include baseline, measurement method and observation window. Never fabricate a numerical improvement where no baseline exists.
